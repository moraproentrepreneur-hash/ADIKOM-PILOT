\# ADIKOM PILOT

\## Design System



\*\*Version :\*\* 1.0  

\*\*Statut :\*\* Référence officielle de conception UI/UX  

\*\*Entreprise :\*\* ADIKOM Technology \& Travel  

\*\*Projet :\*\* ADIKOM PILOT  

\*\*Périmètre :\*\* SaaS interne de gestion et de pilotage



\---



\# 1. Objet du document



Ce document définit les règles visuelles et UI/UX officielles à respecter pour la conception et le développement de \*\*ADIKOM PILOT\*\*.



Il constitue la référence principale pour :



\- l'interface du SaaS ;

\- la landing page ;

\- les tableaux de bord ;

\- les pages de gestion ;

\- les formulaires ;

\- les tableaux ;

\- les fiches détaillées ;

\- les modales ;

\- les notifications ;

\- les composants d'administration ;

\- les documents générés depuis le SaaS lorsque cela est pertinent.



Toute nouvelle interface développée dans ADIKOM PILOT doit respecter ce Design System.



\---



\# 2. Sources officielles



Les ressources suivantes constituent les références visuelles officielles du projet :



\- Logo officiel ADIKOM ;

\- Charte graphique ADIKOM ;

\- présent Design System ;

\- références UI fournies dans le dossier `References\_UI`.



Le logo et les éléments graphiques fournis dans le dossier `06\_Design` doivent être privilégiés par rapport à toute interprétation personnelle.



\---



\# 3. Règle absolue concernant le logo ADIKOM



\## 3.1 Utilisation du logo officiel



Le logo officiel ADIKOM doit être utilisé \*\*tel qu'il a été fourni\*\*.



Il est strictement interdit de :



\- redessiner le logo ;

\- recréer le logo avec du texte ;

\- modifier sa forme ;

\- modifier ses proportions ;

\- modifier ses couleurs ;

\- changer sa typographie ;

\- étirer le logo ;

\- écraser le logo ;

\- incliner le logo ;

\- appliquer une rotation ;

\- ajouter des effets ;

\- ajouter une ombre artificielle ;

\- ajouter un contour ;

\- modifier son symbole ;

\- remplacer une partie du logo ;

\- générer une nouvelle version du logo avec une IA ;

\- utiliser une interprétation approximative du logo.



Le logo officiel doit toujours rester fidèle au fichier source fourni.



\---



\# 4. Préservation des proportions du logo



Le ratio largeur/hauteur du logo doit toujours être conservé.



Lorsqu'une taille différente est nécessaire :



\*\*redimensionnement proportionnel uniquement.\*\*



Aucun étirement horizontal ou vertical n'est autorisé.



\---



\# 5. Logo et espace de respiration



Chaque emplacement prévu pour le logo doit disposer d'un espace suffisant autour du logo.



Le logo ne doit jamais être collé :



\- au bord d'un composant ;

\- à un texte ;

\- à une icône ;

\- à un autre élément graphique.



L'espace autour du logo doit permettre une lecture immédiate et professionnelle.



\---



\# 6. Logo sur fond clair



Sur fond blanc ou très clair, utiliser le logo officiel fourni dans sa version adaptée à ce contexte.



Le logo doit rester parfaitement lisible.



\---



\# 7. Logo sur fond coloré



Lorsqu'un logo doit être placé sur :



\- bleu ADIKOM ;

\- bleu foncé ;

\- image ;

\- fond graphique ;

\- arrière-plan coloré ;



l'emplacement destiné au logo doit disposer d'une \*\*zone suffisamment claire, idéalement blanche\*\*, afin que le logo officiel reste parfaitement visible.



Ne jamais modifier le logo pour tenter de le rendre lisible.



La solution doit être apportée par le \*\*fond ou le conteneur\*\*, et non par une transformation du logo.



\---



\# 8. Logo sur les composants



Lorsqu'un composant utilise le logo, prévoir un espace propre autour du logo.



Exemples :



\- écran de connexion ;

\- landing page ;

\- en-tête ;

\- écran de chargement ;

\- page de profil ;

\- documents ;

\- pied de page ;

\- pages administratives ;

\- éléments de navigation.



Le logo doit toujours être suffisamment grand pour rester identifiable sans prendre inutilement de place.



\---



\# 9. Logo dans la barre latérale



La barre latérale doit pouvoir afficher le logo ADIKOM dans sa partie supérieure.



Lorsque la sidebar est rétractée :



\- le logo doit rester identifiable ;

\- il doit être correctement centré ;

\- il ne doit pas être déformé ;

\- son espace doit rester suffisant.



Si la version complète du logo devient trop large lorsque la sidebar est rétractée, utiliser uniquement une version officielle adaptée si celle-ci est fournie dans les ressources du projet.



Ne jamais fabriquer une nouvelle version du logo.

\# 11. Hiérarchie des couleurs



La couleur dominante de l'interface doit être le \*\*bleu ADIKOM #1E5AA8\*\*.



La hiérarchie générale doit suivre :



\*\*Bleu ADIKOM → Bleu clair → Bleu très clair → Gris foncé → Gris moyen → Blanc\*\*



Ne pas multiplier inutilement les couleurs.



L'interface doit rester :



\- professionnelle ;

\- cohérente ;

\- sobre ;

\- moderne ;

\- facilement lisible.



\---



\# 12. Couleurs fonctionnelles



Les couleurs fonctionnelles peuvent être utilisées pour communiquer un état.



Elles doivent rester sobres et cohérentes avec l'identité ADIKOM.



Exemples :



\### Succès



Utiliser une teinte verte lisible.



Exemples :



\- paiement réussi ;

\- véhicule disponible ;

\- opération validée ;

\- utilisateur actif.



\### Avertissement



Utiliser une teinte jaune/orange.



Exemples :



\- échéance proche ;

\- document arrivant à expiration ;

\- maintenance prévue.



\### Erreur



Utiliser une teinte rouge.



Exemples :



\- erreur ;

\- opération refusée ;

\- paiement échoué ;

\- donnée invalide.



\### Information



Utiliser les nuances bleues ADIKOM.



\---



\# 13. Règle des couleurs fonctionnelles



Les couleurs fonctionnelles ne doivent jamais remplacer les couleurs de marque.



Elles servent uniquement à communiquer un état ou une information.



Ne pas transformer l'interface en une accumulation de couleurs.



\---



\# 14. Typographie



La charte ADIKOM recommande :



\### Titres



\*\*Montserrat / Poppins\*\*



Utiliser principalement :



\- Bold ;

\- SemiBold.



\### Texte courant



\*\*Lato / Source Sans Pro / Inter\*\*



Utiliser principalement :



\- Regular ;

\- Medium ;

\- éventuellement SemiBold pour certains éléments.



\---



\# 15. Règle typographique



La typographie doit privilégier :



\- lisibilité ;

\- hiérarchie ;

\- confort ;

\- cohérence ;

\- sobriété.



Éviter les textes trop petits.



Les interfaces de gestion doivent rester lisibles sur écran desktop comme sur tablette et mobile.



\---



\# 16. Hiérarchie typographique



Utiliser une hiérarchie claire :



\*\*H1\*\*



Titre principal de page.



\*\*H2\*\*



Section principale.



\*\*H3\*\*



Sous-section.



\*\*H4\*\*



Sous-section secondaire.



\*\*Body\*\*



Contenu courant.



\*\*Caption\*\*



Informations secondaires.



\---



\# 17. Titres de page



Chaque page principale doit disposer d'un titre clairement identifiable.



Exemple :



\*\*Gestion de location\*\*



Puis éventuellement :



> Suivez les réservations, départs, retours et disponibilités du parc.



Le titre doit être immédiatement identifiable visuellement.



\---



\# 18. Interface générale



ADIKOM PILOT doit adopter une interface :



\- moderne ;

\- professionnelle ;

\- structurée ;

\- épurée ;

\- dense mais respirante ;

\- orientée productivité.



Le SaaS étant un outil de gestion interne, la priorité doit être :



\*\*efficacité → lisibilité → rapidité → contrôle.\*\*



\---



\# 19. Architecture visuelle



L'interface doit reposer principalement sur :



\- une barre latérale ;

\- une zone de contenu principale ;

\- éventuellement une barre supérieure ;

\- des cartes ;

\- des tableaux ;

\- des formulaires ;

\- des filtres ;

\- des boutons d'action ;

\- des indicateurs.



\---



\# 20. Barre latérale



La sidebar constitue l'un des éléments structurants du SaaS.



Elle doit afficher les modules principaux.



Structure recommandée :



\- logo ADIKOM ;

\- navigation ;

\- modules ;

\- menus ;

\- sous-menus ;

\- profil utilisateur ;

\- déconnexion.



\---



\# 21. Sidebar rétractable



La barre latérale doit être rétractable.



\### État ouvert



Afficher :



\- icône ;

\- nom du module ;

\- menus ;

\- sous-menus.



\### État rétracté



Afficher principalement :



\- icônes ;

\- éléments essentiels ;

\- logo ou élément officiel adapté.



Le passage d'un état à l'autre doit être fluide.



\---



\# 22. Navigation



La navigation doit respecter une hiérarchie claire :



\*\*Module\*\*



→ \*\*Menu\*\*



→ \*\*Sous-menu\*\*



Exemple :



\*\*Tiers\*\*



→ Clients



→ Fournisseurs



→ Partenariats



\---



\# 23. Module actif



Le module actuellement sélectionné doit être immédiatement identifiable.



Utiliser :



\- bleu ADIKOM ;

\- fond légèrement contrasté ;

\- indicateur latéral ;

\- icône active.



Ne pas utiliser de couleurs excessives.



\---



\# 24. Icônes



Les icônes doivent être :



\- simples ;

\- modernes ;

\- cohérentes ;

\- facilement reconnaissables.



Privilégier une même famille d'icônes sur l'ensemble du SaaS.



Éviter de mélanger plusieurs styles graphiques.



\---



\# 25. Boutons



Les boutons doivent avoir une hiérarchie claire.



\## Bouton primaire



Utiliser le bleu ADIKOM.



Exemples :



\- Enregistrer ;

\- Créer ;

\- Confirmer ;

\- Valider.



\## Bouton secondaire



Utiliser une apparence plus discrète.



Exemples :



\- Annuler ;

\- Retour ;

\- Fermer.



\## Action destructive



Utiliser une couleur d'erreur appropriée.



Exemples :



\- Supprimer ;

\- Annuler définitivement ;

\- Désactiver.



\---



\# 26. Boutons et textes



Les libellés des boutons doivent être explicites.



Préférer :



\*\*Créer une réservation\*\*



plutôt que :



\*\*OK\*\*



Préférer :



\*\*Enregistrer le fournisseur\*\*



plutôt que :



\*\*Valider\*\*



lorsque l'action est une simple sauvegarde.



\---



\# 27. Cartes



Les cartes doivent servir à regrouper des informations cohérentes.



Exemples :



\- chiffre d'affaires ;

\- véhicules disponibles ;

\- locations en cours ;

\- notifications ;

\- informations client ;

\- informations fournisseur.



Les cartes doivent rester sobres.



\---



\# 28. Bordures



Les bordures doivent être discrètes.



Privilégier :



\- gris clair ;

\- bleu très clair ;

\- faible contraste.



Éviter les bordures épaisses et omniprésentes.



\---



\# 29. Ombres



Les ombres doivent être légères.



Elles doivent servir à créer une hiérarchie visuelle et non à donner un aspect excessivement décoratif.



\---



\# 30. Rayons des angles



Les composants peuvent utiliser des angles légèrement arrondis.



L'objectif est d'obtenir une interface moderne sans tomber dans un style excessivement arrondi.



La cohérence doit être maintenue sur :



\- boutons ;

\- cartes ;

\- champs ;

\- modales ;

\- tableaux ;

\- badges.



\---



\# 31. Tableaux



Les tableaux sont essentiels dans ADIKOM PILOT.



Ils doivent être :



\- lisibles ;

\- structurés ;

\- rapides à parcourir ;

\- responsifs ;

\- faciles à filtrer.



\---



\# 32. En-têtes de tableaux



Les en-têtes doivent être clairement différenciés du contenu.



Utiliser principalement :



\- bleu ADIKOM ;

\- bleu très clair ;

\- gris clair.



Le texte doit rester parfaitement lisible.



\---



\# 33. Lignes de tableaux



Les lignes doivent être suffisamment espacées.



Lorsque nécessaire, utiliser une alternance très légère des arrière-plans pour améliorer la lecture.



Ne jamais rendre le tableau visuellement lourd.



\---



\# 34. Actions dans les tableaux



Les actions principales doivent être facilement accessibles.



Exemples :



\- Voir ;

\- Modifier ;

\- Archiver ;

\- Supprimer ;

\- Télécharger ;

\- Plus.



Les actions destructives doivent être clairement différenciées.



\---



\# 35. Recherche



Les listes importantes doivent proposer une recherche lorsque cela apporte une réelle valeur.



Exemples :



\- clients ;

\- fournisseurs ;

\- véhicules ;

\- locations ;

\- factures ;

\- utilisateurs.



La recherche doit être immédiatement identifiable.



\---



\# 36. Filtres



Les filtres doivent être présentés de manière simple.



Exemples :



\- statut ;

\- période ;

\- catégorie ;

\- fournisseur ;

\- client ;

\- véhicule.



Éviter de surcharger l'écran avec trop de filtres visibles simultanément.



\---



\# 37. Formulaires



Les formulaires doivent être organisés par sections logiques.



Exemple :



\### Informations générales



\### Coordonnées



\### Informations commerciales



\### Informations financières



\### Documents



\---



\# 38. Champs obligatoires



Les champs obligatoires doivent être clairement identifiables.



Le système doit expliquer les erreurs de saisie directement au niveau du champ concerné.



\---



\# 39. Validation des formulaires



Les erreurs doivent être :



\- visibles ;

\- compréhensibles ;

\- localisées ;

\- facilement corrigeables.



Éviter les messages d'erreur génériques.



\---



\# 40. Fiches détaillées



Les fiches clients, fournisseurs, véhicules, utilisateurs et autres entités importantes doivent avoir une structure claire.



Elles peuvent utiliser :



\- en-tête ;

\- résumé ;

\- informations principales ;

\- onglets ;

\- historique ;

\- documents ;

\- actions.



\---



\# 41. Onglets



Les onglets doivent être utilisés lorsque plusieurs catégories d'informations appartiennent à la même entité.



Exemple pour un utilisateur :



\*\*Utilisateur\*\*



\*\*Permissions\*\*



Cette structure est obligatoire pour le module \*\*Utilisateurs \& Groupes\*\* conformément aux règles métier du projet.



\---



\# 42. Badges de statut



Les statuts doivent être affichés sous forme de badges lorsque cela facilite la lecture.



Exemples :



\*\*Actif\*\*



\*\*Disponible\*\*



\*\*En location\*\*



\*\*En maintenance\*\*



\*\*Payée\*\*



\*\*En attente\*\*



\*\*Annulée\*\*



Les couleurs doivent être cohérentes avec les états fonctionnels.



\---



\# 43. Notifications



Les notifications doivent être facilement identifiables mais ne doivent pas être agressives.



Utiliser principalement :



\- icônes ;

\- badges ;

\- couleurs fonctionnelles ;

\- niveaux de priorité.



\---



\# 44. Centre de notifications



Le Centre de notifications doit pouvoir différencier :



\- information ;

\- rappel ;

\- avertissement ;

\- urgence.



Les notifications importantes doivent être visuellement prioritaires.



\---



\# 45. Modales



Les modales doivent être utilisées avec modération.



Elles conviennent notamment pour :



\- confirmation ;

\- suppression ;

\- annulation ;

\- validation d'une action sensible ;

\- affichage rapide d'informations.



\---



\# 46. Actions destructives



Toute action destructive ou difficilement réversible doit demander une confirmation.



Exemple :



> Êtes-vous sûr de vouloir désactiver cet utilisateur ?



La confirmation doit indiquer clairement la conséquence.



\---



\# 47. Messages de succès



Après une opération réussie, afficher un retour visuel clair.



Exemple :



> Client créé avec succès.



Le message doit être discret mais immédiatement identifiable.



\---



\# 48. États vides



Lorsqu'une liste ne contient aucune donnée, ne pas afficher uniquement une zone blanche.



Afficher un état vide utile.



Exemple :



\*\*Aucun véhicule enregistré\*\*



Puis éventuellement :



\*\*Ajouter un véhicule\*\*



\---



\# 49. États de chargement



Les temps de chargement doivent être représentés de manière professionnelle.



Utiliser :



\- skeletons ;

\- loaders discrets ;

\- indicateurs de progression.



Éviter les écrans entièrement bloqués lorsque cela n'est pas nécessaire.



\---



\# 50. Responsive Design



ADIKOM PILOT doit être \*\*100 % responsive\*\*.



L'interface doit fonctionner correctement sur :



\- ordinateur ;

\- tablette ;

\- smartphone.



\---



\# 51. Desktop



Le desktop constitue l'environnement principal du SaaS de gestion.



L'interface doit exploiter efficacement l'espace disponible tout en conservant une bonne lisibilité.



\---



\# 52. Tablette



Sur tablette :



\- la sidebar peut être réduite ;

\- les tableaux peuvent devenir scrollables ;

\- les cartes peuvent se réorganiser ;

\- les formulaires peuvent passer en une ou deux colonnes.



\---



\# 53. Mobile



Sur mobile :



\- la sidebar doit devenir une navigation adaptée ;

\- les colonnes doivent se réorganiser ;

\- les tableaux doivent être adaptés ;

\- les boutons doivent rester accessibles ;

\- les informations prioritaires doivent rester visibles.



Ne pas simplement réduire l'interface desktop.



\---



\# 54. Espacement



L'interface doit utiliser des espacements cohérents.



Privilégier une respiration suffisante entre :



\- sections ;

\- cartes ;

\- champs ;

\- titres ;

\- tableaux ;

\- boutons.



Le design doit être aéré sans gaspiller inutilement l'espace.



\---



\# 55. Densité de l'interface



ADIKOM PILOT est un logiciel de gestion.



L'interface peut donc être plus dense qu'un site vitrine.



Cependant :



\*\*dense ≠ chargé.\*\*



Chaque élément doit avoir une fonction claire.



\---



\# 56. Landing page



Le SaaS doit disposer d'une landing page professionnelle.



Elle doit présenter :



\- ADIKOM PILOT ;

\- sa mission ;

\- ses principaux bénéfices ;

\- ses fonctionnalités principales ;

\- son positionnement ;

\- son identité ADIKOM.



La landing page doit rester cohérente avec l'interface du SaaS.



> \*\*Décision arbitrée — DEC-003\*\*
>
> Cette exigence devait être conciliée avec le principe « SaaS strictement interne »
> (`README.md` §65, `01\_Vision\_et\_Objectifs/01\_Vision\_ADIKOM\_PILOT.md` §4).
>
> Retenu : landing page publique \*\*institutionnelle uniquement\*\*, puis `/connexion`.
> Aucune donnée métier exposée, aucune création de compte publique.
>
> Voir `08\_Decisions/01\_Journal\_des\_Decisions.md`.



\---



\# 57. Page de connexion



La page de connexion doit être sobre et professionnelle.



Elle doit utiliser :



\- logo officiel ADIKOM ;

\- fond clair ou zone blanche adaptée ;

\- identité ADIKOM ;

\- formulaire de connexion.



Le logo doit être parfaitement lisible.



\*\*Ne jamais modifier le logo pour l'adapter au fond.\*\*



\---



\# 58. Page de connexion — protection du logo



Si un fond bleu ou coloré est utilisé autour du logo, prévoir une zone blanche suffisamment grande derrière le logo.



Le logo officiel doit rester inchangé.



\---



\# 59. Écrans de chargement et logo



Si un écran de chargement utilise le logo ADIKOM :



\- utiliser le fichier officiel ;

\- conserver ses proportions ;

\- ne pas appliquer d'animation déformante ;

\- ne pas changer ses couleurs.



Une animation légère de présence ou d'apparition peut être utilisée uniquement si elle ne modifie pas l'identité du logo.



\---



\# 60. Accessibilité



L'interface doit respecter les principes fondamentaux d'accessibilité.



Veiller notamment à :



\- contraste suffisant ;

\- taille de texte lisible ;

\- états de focus visibles ;

\- boutons compréhensibles ;

\- labels explicites ;

\- navigation cohérente.



\---



\# 61. Contraste



Le texte doit toujours rester lisible sur son arrière-plan.



Le bleu ADIKOM peut être utilisé comme fond avec du texte blanc lorsqu'un contraste suffisant est assuré.



\---



\# 62. Lisibilité



Aucun texte ne doit être :



\- minuscule ;

\- comprimé ;

\- coupé ;

\- superposé ;

\- placé sur un arrière-plan illisible.



\---



\# 63. Cohérence des composants



Un même composant doit avoir le même comportement visuel dans toute l'application.



Exemple :



Un bouton primaire doit rester visuellement cohérent sur :



\- Clients ;

\- Fournisseurs ;

\- Locations ;

\- Factures ;

\- Paramètres.



\---



\# 64. Cohérence des états



Un même état doit conserver la même logique visuelle.



Exemple :



\*\*Actif\*\*



doit être représenté de manière cohérente dans :



\- utilisateurs ;

\- fournisseurs ;

\- véhicules ;

\- clients.



\---



\# 65. Design des dashboards



Les dashboards doivent privilégier :



\- indicateurs clés ;

\- graphiques utiles ;

\- alertes ;

\- tendances ;

\- actions rapides.



Éviter les graphiques décoratifs sans valeur décisionnelle.



\---



\# 66. Hiérarchie du dashboard



L'ordre recommandé est :



\*\*Indicateurs clés\*\*



↓



\*\*Alertes importantes\*\*



↓



\*\*Activité récente\*\*



↓



\*\*Graphiques\*\*



↓



\*\*Détails\*\*



La hiérarchie peut varier selon le rôle de l'utilisateur.



\---



\# 67. Design des graphiques



Les graphiques doivent utiliser principalement les couleurs ADIKOM.



Éviter l'utilisation excessive de couleurs.



Les graphiques doivent être :



\- simples ;

\- lisibles ;

\- interprétables ;

\- utiles à la décision.



\---



\# 68. Design des documents



Lorsque le SaaS génère des documents :



\- respecter l'identité ADIKOM ;

\- utiliser le logo officiel ;

\- respecter les couleurs ;

\- conserver une hiérarchie claire ;

\- prévoir suffisamment d'espace blanc ;

\- garantir la lisibilité à l'impression.



\---



\# 69. Logo dans les documents



Tout document utilisant le logo doit utiliser le fichier officiel.



Le logo doit être :



\- proportionnel ;

\- lisible ;

\- suffisamment grand ;

\- suffisamment dégagé.



Si le logo est placé sur un fond coloré, prévoir une zone blanche ou claire derrière lui.



\---



\# 70. Interdiction des logos générés



Aucune IA ou outil de génération ne doit recréer le logo ADIKOM.



Le fichier officiel fourni dans le projet est la seule source de vérité pour le logo.

\# 74. Règle de choix du format logo



Utiliser le format le plus approprié selon le contexte :



\### SVG



À privilégier pour :



\- interface ;

\- navigation ;

\- composants ;

\- affichage responsive.



\### PNG



À privilégier lorsque :



\- transparence ;

\- compatibilité ;

\- export graphique.



\### WebP



À utiliser lorsque pertinent pour :



\- performance ;

\- web ;

\- certains visuels.



Dans tous les cas :



\*\*le fichier source ne doit pas être modifié.\*\*



\---



\# 75. Règle de qualité du logo



Le logo ne doit jamais apparaître :



\- flou ;

\- pixelisé inutilement ;

\- déformé ;

\- coupé ;

\- trop petit ;

\- illisible.



Lorsqu'il est affiché à une taille importante, utiliser une source suffisamment haute résolution ou le SVG officiel.



\---



\# 76. Protection contre le mauvais contraste



Avant de placer le logo sur un composant, vérifier :



\*\*Le logo est-il immédiatement lisible ?\*\*



Si non :



1\. modifier le fond ;

2\. ajouter une zone blanche ;

3\. modifier l'emplacement ;

4\. augmenter l'espace de respiration.



\*\*Ne jamais modifier le logo.\*\*

\# 77. Style global

\*\*Fiabilité\*\*



\*\*Technologie\*\*



\*\*Organisation\*\*



\*\*Mobilité\*\*



\*\*Efficacité\*\*



\*\*Modernité\*\*

\# 78. Ce qu'il faut éviter



Ne pas produire une interface :



\- trop colorée ;

\- trop arrondie ;

\- trop ludique ;

\- trop minimaliste au point de perdre des informations ;

\- trop chargée ;

\- composée de composants incohérents ;

\- avec des ombres excessives ;

\- avec des gradients inutiles ;

\- avec des animations excessives ;

\- avec des textes trop petits ;

\- avec des logos déformés.

4\. Cohérence du Design System ;

5\. Accessibilité ;

6\. Esthétique.
